@purpose
Prarup never parses Word or LaTeX itself. It asks the program **pandoc** to do it. This file is the only place that talks to pandoc. Every other file calls these functions and gets back plain Python lists and dicts.

pandoc can turn a document into a **JSON tree** (its "AST", abstract syntax tree). Each node is a dict like `{"t": "Para", "c": [...]}`: `t` is the type of the node, `c` is its content. A paragraph holds words (`Str`), spaces (`Space`), maths (`Math`) and so on.

The one trick in this file: starting pandoc takes time, so instead of running it once per paragraph, many pieces are joined with a marker word `PRARUPSEPARATOR`, converted in **one** run, and split again afterwards.

@imports
`json` reads and writes pandoc's JSON. `re` is used by `_one_line`. `find_tool` and `run_tool` come from `process.py`, which finds the pandoc program and runs it without opening a console window on Windows.

== PandocNotFound
An exception class of our own. `pass` means the class adds nothing: it is just a new name for "something went wrong", so the window can show "pandoc is not installed" instead of a confusing traceback.
* Custom exception hierarchy: specific error classes let each caller catch exactly the failure it can handle.
? Why make an empty class instead of raising Exception?
! So callers can catch exactly this error with `except PandocNotFound`, and the name tells the reader what went wrong.
? What does inheriting from Exception give it?
! Everything an exception needs: it can be raised, caught, and carries a message.

== PandocFailed
Raised when pandoc ran but returned a non-zero exit code, for example on a broken .docx. It carries pandoc's own error text.
? What is the difference between PandocNotFound and PandocFailed?
! NotFound: the program is not installed. Failed: it is installed, ran, and reported an error about the file.

== _run
Runs pandoc once with the given arguments and returns what it printed (its standard output) as a string.
- `find_tool("pandoc")` looks for the program; if missing, raise `PandocNotFound`.
- `[pandoc, *args]` builds the command: the `*` unpacks the list into the new list.
- `input=stdin` sends text to pandoc as if typed on its keyboard; used when we convert strings instead of files.
- Exit code 0 means success; anything else raises `PandocFailed` with pandoc's message.
The leading underscore in `_run` is a Python convention meaning "private to this file".
* Single Responsibility: this is the only function in Prarup that starts pandoc. If pandoc's command line changes, only this function changes.
? What does `*args` mean in `[pandoc, *args]`?
! It unpacks the list: `[pandoc, *["-f","json"]]` becomes `[pandoc, "-f", "json"]`.
? Why `result.stderr.strip() or "pandoc failed"`?
! `or` returns the right side when the left is empty, so there is always some message.
? What is returncode?
! The number a program returns when it exits. 0 means success by convention.

== read
Reads a .docx or .tex file and returns pandoc's whole JSON tree as a Python dict.
- The format is chosen from the file extension: `.docx` means Word, anything else LaTeX.
- For Word, images live inside the .docx zip. `--extract-media=.` makes pandoc write them out; it is run inside `media_dir` (`cwd=media_dir`) so they land in our project folder.
- For LaTeX, pandoc runs in the paper's own folder so `\input{sections/intro}` resolves.
- `json.loads` turns pandoc's JSON text into dicts and lists.
> read("paper.docx", project) -> {"pandoc-api-version": [...], "meta": {...}, "blocks": [ {"t":"Header",...}, {"t":"Para",...}, ... ]}
? Why `--extract-media=.` and not `--extract-media=media`?
! pandoc adds its own `media` folder; with `=media` the images would end up in `media/media/`.
? What is json.loads vs json.load?
! `loads` reads from a string (s for string); `load` reads from an open file.

== table_rows
A pandoc table is a 6-part list: attributes, caption, column specs, head, bodies, foot. This pulls every row out into one list (head rows first, then each body's rows, then foot rows) and also returns how many rows were header rows.
- `_, _, _, head, bodies, foot = table["c"]` is tuple unpacking; `_` means "I do not need this one".
- A body is itself `[attr, row_head_columns, intermediate_head_rows, rows]`, so `body[2] + body[3]` adds both row lists.
? What does `_` mean in the unpacking?
! A throwaway name: the value is assigned but we promise not to use it.
? Who uses table_rows?
! The table editor (to draw a grid of cells) and the renderer (to write LaTeX tables).

== stringify
Turns any piece of the pandoc tree into plain text, the way a human would read it.
It defines a **nested function** `walk` that calls itself on every child (recursion) and appends words to the list `out`:
- `Str` adds the word; `Space` adds a space; `LineBreak` a newline.
- `Math` and `Code` add their text (stored at `c[1]`).
- Images and footnotes add nothing.
- Block nodes (paragraphs, headers) add a newline after themselves, so table cells do not run together.
- `Quoted` adds curly quotes around its content.
- Anything else: just walk into its children.
At the end, every line has its extra spaces squeezed (`" ".join(line.split())`) and empty lines are dropped.
> stringify({"t":"Para","c":[{"t":"Str","c":"Deep"},{"t":"Space"},{"t":"Str","c":"learning"}]})  ->  "Deep learning"
? Why is walk defined inside stringify?
! It needs to append to `out`, which belongs to this one call; a nested function can see it without passing it around.
? Why build a list and join it, instead of adding strings with +=?
! Joining a list once is the standard fast way; repeated `+=` on strings copies the text each time.
? What does `" ".join(line.split())` do?
! `split()` with no argument breaks on any run of whitespace, so joining with one space collapses many spaces into one.

== blocks_to
Converts many lists of pandoc blocks to another format (Markdown or LaTeX) in **one** pandoc run.
- After each piece it appends a paragraph containing only `PRARUPSEPARATOR`.
- It builds a tiny pandoc document (`api` is the version number pandoc gave us when reading) and sends it as JSON on stdin.
- The output text is split on the separator; the first `len(pieces)` parts are the answers, in order.
> blocks_to([[para1], [para2, para3]], api, "markdown")  ->  ["text of para1", "para2\n\npara3"]
* Batching (a performance pattern): many small requests are combined into one expensive call.
? Why not call pandoc once per block?
! A paper has hundreds of blocks; starting a program hundreds of times takes many seconds. One run with separators takes a fraction of a second.
? What if a paragraph itself contained the word PRARUPSEPARATOR?
! The split would go wrong. It is a made-up word chosen so no real paper contains it.

== markdown_to_blocks
The reverse of `blocks_to`: takes several Markdown strings, joins them with the separator, asks pandoc for JSON, then walks the blocks and starts a new group each time it meets the separator paragraph.
? Why does the loop append `current` once more after it ends?
! The last group has no separator after it, so it must be added by hand.

== _one_line
Prepares a caption or short text so pandoc does not misread it as Markdown structure.
- First it squeezes the text onto one line.
- A leading `-`, `*`, `+`, `#` or `>` would make Markdown read a list, heading or quote, so a backslash is put in front (`\-`).
- A caption like `a. Training loss` would become a numbered list; `a\.` stops that.
> _one_line("1. Accuracy over rounds")  ->  "1\. Accuracy over rounds"
? What is `\1` in the replacement?
! It puts back what the first bracket group of the pattern matched.
? Why did we need this function?
! A real caption beginning "a." was turned into a LaTeX list and broke the PDF.

== markdown_to_latex
Converts many Markdown strings (captions, abstract, paragraphs) to LaTeX in one run. Empty strings are not sent to pandoc at all; they come back as "" in their original position.
- `filled` keeps only the non-empty texts.
- `iter(...)` makes an iterator over pandoc's answers; `next(converted)` takes the next one each time a non-empty text is met.
? Why skip empty texts?
! pandoc turned an empty abstract into `\hspace{0pt}`, which printed an empty Abstract heading in the PDF.
? What does iter and next do here?
! `iter` makes a one-way cursor over the answers; each `next` call gives the next answer, so answers are matched to non-empty texts in order.

== latex_to_markdown
Converts LaTeX snippets (for example an abstract read from a .tex file) to Markdown, in one run, and squeezes each to a single line.
? Why convert LaTeX to Markdown at all?
! Inside Prarup every text is stored as Markdown, whatever the input was. One format means one editor and one renderer.
